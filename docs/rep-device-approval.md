# Rep browser approval

One approved browser per rep is enforced through an additive D1 migration (`0006`), a server-generated HttpOnly `asad_device` cookie, and sessions bound to its approved record. Only the hash is stored in D1. This identifies a browser profile, not IMEI or physical hardware. Copying the entire profile/credentials is outside this protection.

After deployment, existing unbound rep sessions require a fresh login and manager approval. Admin and warehouse sessions keep their existing behavior. Correct rep credentials register a pending device without a session or access to company data. The manager reviews the code in **المناديب → أجهزة المناديب** and explicitly approves/rejects it with a reason. Approval replaces the previous device; rejection leaves the current approved device intact. Approval/revocation deletes that rep's sessions atomically with its audit event, under the office revision guard. Every authenticated API uses the central device-aware `current()` check. Password changes retain the approved browser.

Offline snapshots receive a public device grant with the existing seven-day session expiry. Old unbound/expired snapshots cannot open offline or create local sales. Revocation cannot be observed by a disconnected browser until it reconnects; its server writes and synchronization are then refused. Local sale rows are never removed by a device decision or logout. Sync them before replacing a device when possible. Reapprove the old device to finish syncing, or export/import its local sale recovery file on the newly approved browser. Clearing browser storage can erase unsynced local sales, as before.

Business backups/restores retain current authentication accounts and device approvals; they neither export browser secrets nor restore old sessions. Source rollback can use version 48 / commit `e0e2bfa1be98e78f44d2cca5bfa966f7821948e8`; the migration is additive and should not be reversed destructively. Rolling back to that source removes device enforcement, so do so only as an explicitly authorized rollback. Do not restore old company data merely to roll back code.

Verification: `node tests/run-api.mjs tests/rep-device-api.test.mjs` checks pending/approved/rejected/revoked flows, session-only copying denial, manager permission and reason checks, stale reviews, own-device replacement, password continuity, unchanged financial records, and exact-once synchronization of an existing local invoice after reapproval. Existing API fixtures explicitly obtain manager approval through the actual endpoint; there is no production auto-approval/test bypass.
